# Architecture

## Project Philosophy

This project is not just another interview questions website.

Its primary goal is to demonstrate software engineering practices while providing a fast, maintainable, and community-driven knowledge base for technical interviews.

The application follows a data-driven architecture where content is completely separated from presentation.

All interview content is maintained in the companion repository and exposed as a generated static JSON API. The website is only responsible for fetching, caching, searching, and presenting that data.

Every architectural decision in this project follows four principles:

- Simplicity over cleverness
- Server-first rendering
- URL as the source of truth
- Scalability without rewrites

The project should continue working even when new domains, topics, languages, or questions are added to the data source without requiring code changes.

## Overview

This project follows the Feature-Sliced Design (FSD) architecture.

The application is designed to consume a generated JSON API produced by the companion repository:

Developer Interview Handbook

The website is responsible only for presenting data.

All content processing, parsing, validation, and generation happen in the generator project.

Feature-Sliced Design encourages clear separation of responsibilities.

Each layer has a single purpose.

This keeps the project maintainable as it grows.

## Why Next.js App Router?

App Router enables:

- React Server Components
- Streaming
- Nested layouts
- Better server-side caching
- Better metadata handling
- Cache Components and Partial Prerendering

---

## Why React Server Components?

Server Components reduce client-side JavaScript.

Benefits:

- Smaller bundles
- Faster rendering
- Better SEO
- Improved performance

Client Components are only used when interactivity is required.

---

## Why Cache Components?

The content API consists of generated static JSON resources that are safe to share between visitors.

Next.js Cache Components allow stable server-side data to be cached while request-specific data remains dynamic.

This provides:

- Reuse of stable generated JSON across requests
- Partial Prerendering
- Clear separation between stable data and runtime request data
- Server-first rendering without introducing a separate caching library

The application enables Cache Components through `cacheComponents: true` in `next.config.ts`.

See [`caching.md`](./caching.md) for the implementation rules.

---

## Why JSON API?

The website consumes static JSON files generated by another repository.

Benefits:

- No backend required
- CDN-friendly
- Extremely cacheable
- Easy to version
- Easy to deploy

---

## Why Static Generation?

Most interview content rarely changes.

Static generation provides:

- Fast loading
- Excellent SEO
- Global CDN caching
- Low infrastructure cost

## Design Principles

- Server First
- URL is the source of truth
- Data-driven UI
- No deep imports
- Clear public APIs
- Composition over duplication
- Stable data should be cached
- Request-specific runtime data should remain outside cache boundaries
